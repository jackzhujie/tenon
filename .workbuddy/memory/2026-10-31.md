## v1.2 定案：数据库两档化 + 插件分发三阶段 + Electron/SaaS 正交（DESIGN v1.2）
用户三问：① 数据库麻烦，换 SQLite？② 有/无 Electron 做 SaaS 的区别与对应用能力的影响？③ 插件先官方维护、后续进 Hub

### 1) 数据库（用户选「PGlite 默认 + PG 发布」）
- 诊断：麻烦的不是 PG，是"让原生 PG 在用户机器上跑起来"；四档里三档都在解决这件事
- **四档 → 两档 + 两逃生口**：
  - `pglite`（默认）：`@electric-sql/pglite` 0.5.13 + `pg-gateway` 0.3.0-beta.4，WASM 版 PG 暴露 TCP，TypeORM 走标准 pg driver，~3.7MB，零原生二进制
  - `postgres`（发布）：compose 内置 postgres:18-alpine / external / 云托管
  - 逃生口：`embedded`（embedded-postgres，移出默认路径）、`sqlite`（仅极端降级，会引入方言分裂）
- **否决纯 SQLite 的两条理由**：① 方言分裂（jsonb/数组/timestamptz/全文检索，本地通上云炸）② AI 生成质量（SQLite 动态类型静默通过 vs PG 报错）
- **PGlite 四个坑**：单连接串行（pool.max=1~2）｜性能 1/3~1/5｜PostGIS 类扩展不可用（但 pgvector 可用，走 `@electric-sql/pglite/vector`）｜0.x 需锁版本
- **连带优化**：产品库 better-sqlite3 → **`node:sqlite`**（Electron 内置 Node 22 自带，消除 `@electron/rebuild`）→ **整个安装包内无任何需按平台编译的原生模块**
- ⚠️ 关键前置验证（已查证）：Electron 内置 Node 确有 `node:sqlite`（实测记录 Electron 37.10.3/Node 22.21.1 = SQLite 3.50.4）→ pi-durable 在 ELECTRON_RUN_AS_NODE 下可用，这条之前没验证过、其实是致命点
- 待补 spike：PGlite + pg-gateway + TypeORM 在 pool.max=1~2 下的稳定性与 P95 延迟（**本方案唯一真实技术风险**）

### 2) Electron 与 SaaS 是正交的（写入 §2.4）
- Electron 不是 SaaS 前置；桌面版/自托管/SaaS 共用同一份 server 代码，只换跑的位置
- Electron 给的是四项本地特权：本地文件、本地命令、OS 密钥链、离线 → 这才是"应用能做什么"的分界
- **SaaS 不是桌面版超集，是互补**：桌面赢"能碰本地资源 + 数据不出本机"，SaaS 赢"在线 + 分享 + 多人"
- SaaS 化成本不在 Electron，在六项 adapter：多租户隔离（gondolin 在 Linux 才是主战场）｜fs→S3｜safeStorage→KMS｜PGlite→托管 PG｜认证计费配额｜长连接负载均衡
- 判断标准：本地能力有没有抽象成接口。`db-provisioner`/`NodeExecutionEnv`/`SecretStore` 是给 SaaS 留的插槽
- M7 可选形态：SaaS + 桌面客户端做"本地能力代理"（Figma 桌面版路子），安全模型复杂，M6 前不碰

### 3) 插件分发三阶段（L2 先官方独家）
- Phase 1（M5）bundled 内置 `resources/plugins`｜Phase 2（M6）Hub 官方独源 `~/.tenon/plugins`｜Phase 3（M7+）第三方上架
- **同一套 manifest + 同一个加载器**，只差 `source` 字段；解析优先级 **hub 版 > bundled 版**（覆盖层）→ **内置插件也能热更新**，卸载 hub 版自动回落
- manifest 字段现在定死：id/version/source/minTenonVersion/signature/permissions/agentHints/pricing
- **顺带闭环两个待办**：市场审核策略→M7；收费组件结算→M6 末（bundled 阶段不需要 license）
- M5 就要做 Plugins 页面（含"Hub 筹备中"占位），否则 M6 会同时面对加载器改造+UI 重构+更新机制三件事

### 两个包的工具定义**不一样**（必须过 adapter，这是铁律 3 的第二个落地点）
| | pi-coding-agent | pi-durable |
|---|---|---|
| 签名 | `execute(toolCallId, params, signal, onUpdate, ctx)` | `execute(args, api, context)` |
| 返回 | `AgentToolResult{content,details,isError}` | `ToolExecutionResult{output,details,isError}` |
| 流式 | `onUpdate(累计快照)` | `api.output(增量)` |
| 上下文 | `ExtensionToolContext`（UI/会话一大坨） | chord `Context`（`abortSignal`） |

- `ctx` 直接传 `undefined` 就行：bash 关掉 `exposeSessionEnvironment`，read/write/edit 不碰 ctx
- 快照 → 增量：前缀差量下发；快照被截断后不再是前缀就停止实时推流（最终结果仍完整）
- **`edit` 入参是 `edits: [{oldText, newText}]`**，不是 old_string/new_string
- **`section()` 的 key 必须 `/^[a-z][a-z0-9_-]*$/`**：`tenon.workspace` 会让每轮 submit 抛 INTERNAL（点号不合法）

### 顺手修掉的两个真问题
1. **`app.status` 之前只写库不推事件** → 前端无从判断"这一轮结束了吗"（等 git.commit 也不行：无改动时没有提交）。
   现在 `chat.ts` 的 `setStatus()` 同时落库+推事件，且**先 commit 再发 idle**（前端看到空闲时版本列表必须已是新的）
2. **submission 的 settle 回调可能晚于 `close()`** → db 已关，写状态抛 `database is not open` → unhandled rejection
   （症状：33 项测试全过但有 2 个 error）。加 `closed` 门 + setStatus 内 try/catch

### 测试
- `packages/server/test/support.ts`：boot/rpc/openSse 夹具（"先连后发"只此一份实现）
- `tools.test.ts` 5 项：写文件（含 git commit 断言）/ 编辑 / 跑命令 / 越界拒写 / 重启后工具集仍在
- 闸门用 `app.status: idle`，**不要**等 `git.commit`（无改动就没有，会挂到超时）
- faux 驱动工具：`model.script([{tool:'write', args:{...}}, {text:'...'}])`；
  `fauxAssistantMessage([fauxToolCall(...)], { stopReason: 'toolUse' })` —— 少了 stopReason 不会执行工具
