## 导出静态包（§4.38）：DESIGN §13.1 的第二种产物第一次真的存在

### 起因是三个问题
用户问：Docker 是否必要（一键打包脚本够不够）／多端打包能否改 GitHub Action／跨应用总闸有必要吗、
token 粒度是什么。查证后发现关键事实：**`export.*` 一个 RPC 都没有**（不只是缺 Dockerfile）。
DSIGN §13.1 的三种产物只有 git push（本地裸库）落地。

### 结论（已与用户对齐）
- Docker **不能省**（它解决"运行环境可复现"6 件事，静态包只解决 2 件），但顺序要反过来：
  **先静态包，Docker 从它派生**（Dockerfile = COPY 产物）。验证放 CI（runner 自带 Docker）
- 多端打包**应该**改 GitHub Action，但第一步是质量门禁（无账号依赖），三平台打包第二步；
  且仓库**还没有 remote**，workflow 写了要推上去才生效
- 总闸要区分**熔断（per-app，已有）vs 总闸（global，缺）**；`setting-keys.ts` 里那句
  "为什么按应用而不是全局"讲的是熔断，不是总闸。token 粒度：按应用是唯一准的一层
  （`harness.usage()`），按角色做不了（欠账⑤）

### 落地
`packages/server/src/export.ts`（390 行）+ `export.static` RPC + 发布对话框入口。
产物：dist/ dist-server/ node_modules(prod) serve.mjs start.sh .env.example README.md。
四个决定：产物不含 pglite；单端口靠生成的 serve.mjs（不改模板）；跑模板自己的 build；
默认带 prod 依赖。实现时发现"从没起过预览就导出"会缺 node_modules → 复用 `ensureDeps`。
